# 协议升级机制基础知识 — Upgrade Header Smuggling 前置理解

> 本文档整理自对 Upgrade Header Smuggling 原理的逐层追问，覆盖从协议分层到漏洞根因的完整链路。
> 建议在阅读 [README.md](README.md) 之前先阅读本文档。

---

## 1. TCP → TLS → HTTP 的分层

访问 `https://example.com` 时，连接建立的顺序是三步：

```
客户端                                               服务器

① TCP 三次握手（建立可靠传输通道）
  ──── SYN ─────→
  ←── SYN+ACK ───
  ──── ACK ─────→
  ✅ TCP 连接建立

② TLS 握手（在 TCP 之上建立加密层）
  ──── ClientHello ──→
       ├ 支持的 TLS 版本
       ├ 支持的加密套件
       └ ALPN 扩展: ["h2", "http/1.1"]

  ←── ServerHello ────
       ├ 选定的 TLS 版本
       ├ 选定的加密套件
       └ ALPN 扩展: "h2"

  ←── Certificate ────
  (密钥交换...)
  ✅ TLS 加密通道建立

③ HTTP 通信（在 TLS 加密通道内传明文 HTTP）
  ═══ 以下所有内容经 TLS 加密 ═══

  ──── GET /index.html ──→
  ←── 200 OK, <html>.. ───
```

关键：**TLS 握手（②）在 HTTP 通信（③）之前完成。ALPN 是 TLS 握手的一部分，在第一个 HTTP 字节发送之前就已经完成了应用层协议的协商。**

---

## 2. ALPN 是什么

ALPN（Application-Layer Protocol Negotiation）是 TLS 的一个扩展字段。它解决的问题是：同一对 IP:Port 上，客户端和服务器可能支持多种应用层协议，需要在加密通道建立的同时确定用哪个。

```
TLS ClientHello 中：
  ALPN Extension = ["h2", "http/1.1"]
                    ↑     ↑
                    |     ── 备选，如果服务器不支持 HTTP/2
                    ──────── 首选 HTTP/2 over TLS

TLS ServerHello 中：
  ALPN Extension = "h2"    ← 服务器选定一个
```

h2 和 http/1.1 是 IANA 注册的标准 ALPN token。如果没有 ALPN，就必须先用 HTTP/1.1 通信，再用 Upgrade 头切换——多浪费一个往返（30-200ms）。

---

## 3. HTTP/1.1 Upgrade 机制

HTTP/1.1 的 `Upgrade` 头部（RFC 7230 §6.7）的目的：**在已经建立好的 HTTP/1.1 连接上，把应用层协议从 HTTP/1.1 切换到另一个协议**。

典型用例 WebSocket：

```
客户端                                  服务器

  ──── GET /chat HTTP/1.1 ──→           一次正常的 HTTP/1.1 请求
       Upgrade: websocket
       Connection: Upgrade

  ←── 101 Switching Protocols ───       服务器同意切换

  ═══ WebSocket 帧 ═══════════════      此后字节不再是 HTTP 格式
```

关键区别：

| | ALPN | HTTP Upgrade |
|---|---|---|
| 发生时机 | TLS 握手阶段（HTTP 通信开始前） | HTTP 通信已经开始后 |
| 需要 TLS | 是 | 否（明文 HTTP/1.1 上也可工作） |
| 效率和往返 | 0 额外往返 | 多一个 101 往返 |

## 4. HTTP/2 的两种协商路径

### 背景：HTTP/1.1 的性能瓶颈

HTTP/1.1 存在**队头阻塞**（Head-of-Line Blocking）：

```
客户端 → [请求1] [请求2] [请求3]
         ← [响应1] [响应2] [响应3]

如果响应1很慢，响应2和3即使已准备好也要等。
```

虽然浏览器会开 6 个并发连接缓解，但每个连接内部仍串行。每个请求还要重复发送臃肿的 HTTP 头部（Cookie、User-Agent 等），浪费大量带宽。

Google 在 2009 年提出 SPDY 协议解决这些问题——多路复用、头部压缩、服务器推送。IETF 于 2015 年基于 SPDY 标准化了 HTTP/2（RFC 7540）。

### IETF 的妥协：h2 与 h2c

HTTP/2 标准化过程中最大的争论：**是否强制 TLS？**

**TLS 强制派**：互联网已在向加密迁移；中间件对明文 HTTP 有各种"意外修改"行为，TLS 可防止；浏览器厂商（Chrome、Firefox）明确表示浏览器端只实现 h2，不实现 h2c。

**反对派**：并非所有 HTTP 通信都在浏览器里发生。内网微服务通信、IoT 设备、嵌入式系统中，TLS 有实际成本——证书管理轮换、握手计算开销、调试困难（无法直接抓包看明文）。

最终 IETF 没有强制 TLS，但定义了两种模式：

| 标识 | 含义 | 协商方式 | 使用场景 |
|------|------|----------|---------|
| `h2` | HTTP/2 over TLS | TLS-ALPN（TLS 握手阶段） | HTTPS 连接（浏览器） |
| `h2c` | HTTP/2 cleartext | HTTP/1.1 Upgrade 头部 | 内网微服务通信、CDN 回源 |

RFC 7540 §3.2 明确规定：`h2` 仅用于 ALPN，不可用于 HTTP/1.1 Upgrade。`h2c` 仅用于 HTTP/1.1 Upgrade。

### 为什么没有 TLS 就必须用 Upgrade？

h2c 不走 TLS，自然没有 ALPN（ALPN 是 TLS 的扩展字段，没有 TLS 就没有 ALPN）。要在明文连接上告诉服务器"我想讲 HTTP/2"，只有两个方案：

**方案 A — 直接发送（Direct HTTP/2）**：TCP 连接建立后直接发送 HTTP/2 前言帧（`PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n`）。问题：服务器怎么知道第一个字节是 HTTP/1.1 还是 HTTP/2？要么约定特定端口（麻烦），要么探测（慢且不优雅）。

**方案 B — 先 HTTP/1.1 再升级（HTTP Upgrade）**：先以 HTTP/1.1 通信，发送 `Upgrade: h2c`，服务器返回 101 后双方切换到 HTTP/2。优势：复用现有 HTTP/1.1 基础设施（端口、路由），无需网络配置改动，向后兼容。

IETF 同时保留了两种方式，但 Upgrade 更实用——在现有 80 端口上就能工作。

## 5. h2c 的实际使用场景

h2c 在**浏览器领域从未实际使用过**（Chrome/Firefox 不实现它）。它的实际价值在：

```
场景一：gRPC 微服务通信
  服务A ── h2c (明文) ──→ 服务B
  gRPC 底层基于 HTTP/2。同数据中心内 TLS 无安全收益但有开销。
  直接 h2c 通信更高效。

场景二：反向代理到后端
  客户端 ── h2 (TLS) ──→ Nginx ── h2c (明文) ──→ 后端应用
  代理对外提供 TLS，内部通过 h2c 转发，
  保持 HTTP/2 多路复用的性能优势（相对于降级到 HTTP/1.1）。

场景三：CDN 回源
  CDN 节点 ── h2c ──→ 源站
  使用 h2c 回源减少连接数和延迟。
```

在以上场景中，双方通信发生在受控的内网环境，TLS 不必要。h2c 提供了 HTTP/2 的性能优势，同时省去了 TLS 的开销。

## 6. 为什么 H2 不会被走私，H2C 会？

**核心：不是加密挡住了代理的眼睛，是 101 状态码触发了代理的"下班"逻辑。**

### H2（TLS + ALPN）：代理始终在 HTTP 解析路径

```
客户端                    反向代理                     后端
  │                         │                          │
  │  ──── TLS ClientHello ─→│                          │
  │      ALPN: h2           │                          │
  │                         │  ← 代理记住: 这是 HTTP/2  │
  │                         │                          │
  │  ════ TLS 加密通道建立 ═══│                          │
  │                         │                          │
  │  ──── HTTP/2 Frame ────→│  ──── HTTP/1.1 ────────→│
  │      :path: /admin      │      GET /admin          │
  │                         │                          │
  │                         │  ← 代理解析每帧           │
  │                         │    提取 :path             │
  │                         │    做 ACL 检查            │
  │  ←─── HTTP/2 Frame ─────│  ←─── HTTP/1.1 ─────────│
  │      :status: 403       │      403 Forbidden       │
```

TLS 握手阶段 ALPN 已告知代理"这是 h2"。代理从第一帧起就在 HTTP 帧解析模式下工作，从未离开。永远不会触发"隧道"代码路径。

### H2C（HTTP/1.1 + Upgrade）：代理被 101 "踢出" HTTP 解析路径

```
客户端                    反向代理                     后端
  │                         │                          │
  │  ──── HTTP/1.1 ────────→│  ──── HTTP/1.1 ────────→│
  │      Upgrade: h2c       │      Upgrade: h2c       │
  │                         │                          │
  │  ←─── HTTP/1.1 ─────────│  ←─── HTTP/1.1 ─────────│
  │      101 Switching      │      101 Switching       │
  │                         │                          │
  │                         │  ← 代理: "协议切换了，    │
  │                         │    我进入隧道模式"        │
  │                         │                          │
  │  ════ HTTP/2 帧 ════════╪══════ HTTP/2 帧 ════════→│
  │      :path: /admin      │      :path: /admin      │
  │                         │                          │
  │                         │  ← 代理不解析！盲传！     │
  │                         │    (虽然是明文 HTTP/2)    │
```

关键逻辑链：

1. 代理为了支持 WebSocket，实现了 "Upgrade 请求 → 101 响应 → 进入隧道（TCP 盲传）" 机制
2. 代理**不区分** Upgrade 的值是 `websocket` 还是 `h2c`——只检查是否收到 101
3. 隧道内跑的是明文 HTTP/2，代理完全有能力解析，但代码已经不解析了
4. 所有 L7 策略（ACL、WAF、认证）全部失效

```
代理的能力始终没变——它完全有能力解析明文 H2C 的 HTTP/2 帧。
但 Upgrade 机制的设计意图就是"收到 101 后放手"。
代理不区分 WebSocket 的 101 和 H2C 的 101，一视同仁地进入隧道模式。
```

## 7. 能否发送 `Upgrade: h2` 绕过代理？

**规范层面**：`h2` 不是合法的 Upgrade token。RFC 7540 §3.2 规定 h2 仅用于 ALPN，不可用于 HTTP/1.1 Upgrade。严格遵循 RFC 的后端会直接忽略或拒绝。

**实现层面**：取决于后端代码。如果后端宽松到"看到 Upgrade 头部不管值是什么都接受升级"，那么：

```
                      规范是否允许  后端是否接受    代理是否进入隧道
Upgrade: websocket       ✅           ✅            ✅（只要后端回 101）
Upgrade: h2c             ✅           ✅            ✅（只要后端回 101）
Upgrade: h2              ❌        取决于实现       ✅（只要后端回 101）
Upgrade: foobar          —         取决于实现       ✅（只要后端回 101）
```

攻击效果上三者无差别——只要后端回 101，代理就进隧道。区别在于**有多少后端会响应**：h2c 有框架支持（Golang、gRPC），h2 作为 Upgrade token 没有任何框架为它写支持代码。

此外 `Upgrade: h2` 存在语义矛盾——h2 表示 HTTP/2 over TLS，但代理到后端已是明文。大多数后端会降级处理：既然连接是明文，就按明文 HTTP/2（即 h2c）处理。这不会阻塞攻击。

## 8. h2c 的设计漏洞根源

h2c 的设计前提是**通信双方之间的网络是可信的**——一端发起 Upgrade，另一端接受升级，中间的链路不需要干预。

```
原始设计：
  客户端 ──── h2c ────→ 服务器
  双方直接协商升级，没有第三方

实际部署：
  客户端 ───→ 代理 ─── h2c ───→ 后端
               ↑
           代理在中间，它看到 101 后进入了隧道模式
           但代理不知道这个隧道里跑的协议其实是自己能解析的 HTTP/2
```

h2c 的 Upgrade 机制**借用了 WebSocket 的隧道基础设施**。代理实现者看到 `Upgrade + 101` 一律按 WebSocket 处理——进入隧道。这对 WebSocket 合理（二进制帧代理确实无法解析），对 h2c 不合理（明文 HTTP/2 代理完全有能力解析），但由于两者共用同一套升级机制，代理无法区分。

## 9. h2c 走私攻击流程（汇总）

```
客户端                    反向代理                     后端
  │                         │                          │
  │  ──── TLS 握手 ────────→│                          │
  │      ALPN: http/1.1    │                          │  ← ALPN 说 http/1.1
  │                         │                          │    不说 h2
  │  ════ TLS 加密 ════════╪                          │
  │                         │                          │
  │  ───TLS 内的 HTTP/1.1──→│  ──── HTTP/1.1 ────────→│
  │   GET /public           │  GET /public             │
  │   Upgrade: h2c          │  Upgrade: h2c            │
  │   Connection: Upgrade   │  Connection: Upgrade     │  代理转发 Upgrade 头部
  │                         │                          │
  │                         │  ← 后端支持 h2c          │
  │  ←──TLS 内的 HTTP/1.1───│  ←─── 101 Switching ────│
  │                         │                          │
  │                         │  ← 代理进入隧道模式       │
  │                         │    不再解析后续流量       │
  │                         │                          │
  │  ═══TLS 内的 H2 帧══════╪══════ H2 帧 (明文) ═════→│
  │   :path: /flag          │   :path: /flag           │
  │                         │                          │
  │                         │  ← 代理 ACL: "禁止 /flag"│
  │                         │    但已经不管了           │
  │  ═══TLS 内的 H2 帧══════╪══════ H2 帧 (明文) ══════│
  │   :status: 200          │   :status: 200           │
  │   "You got the flag!"   │   "You got the flag!"    │
```

RFC 违规点：
- h2c 升级应该发生在端到端明文连接，而非 TLS 连接内部的明文段
- HTTP2-Settings 是 hop-by-hop 头部，代理不应转发（RFC 7540 §3.2.1）
- 代理应对非 WebSocket 的 Upgrade 进行限制

curl 等标准客户端拒绝在 HTTPS 上发起 h2c 升级。h2csmuggler 使用自定义 TCP 连接绕过此限制。

## 10. 一句话总结

**h2c 是为了去掉 TLS 开销、突破 HTTP/1.1 队头阻塞而被设计出来的明文 HTTP/2。它技术上可被代理解析，但因为借用了 WebSocket 的升级机制（Upgrade + 101 → 隧道），代理收到 101 后直接进入隧道模式，不再检测后续内容。h2c 走私正是利用这个"隧道盲区"绕过代理的所有 L7 安全策略。**

## 11. Burp Suite 实操：Repeater 标签与 TCP 连接

### 11.1 不同标签使用不同 TCP 连接

Burp Repeater 中**每个标签（tab）拥有独立的 TCP 连接**。这对于 h2c 走私攻击有直接影响：

```
Repeater Tab 1          Repeater Tab 2
    │                        │
    │── TCP 连接 A ──→       │── TCP 连接 B ──→ 代理
    │                        │
    │  成功打通 h2c 隧道      │  独立的新连接
    │  (Upgrade → 101)       │  代理仍处于 HTTP/1.1 解析模式
    │                        │
    │  后续可发 H2 帧        │  发 Upgrade → 又要重新打隧道
```

**结论**：如果在一个 Repeater 标签中成功完成 Upgrade 握手、进入隧道模式，后续的利用（发 H2 帧访问内部路径）**必须在同一个标签中完成**。切换到另一个标签意味着使用新的 TCP 连接，需要重新执行 Upgrade 握手。

### 11.2 Repeater 的 HTTP/2 协议选项

Burp Repeater 的 Inspector 面板提供了一个协议切换功能，允许在 "HTTP/1" 和 "HTTP/2" 之间选择。但这个选项的语义需要理解清楚：

```
Repeater 协议选择的意义：

  选择 HTTP/1 → Repeater 用 HTTP/1.1 格式构造请求
                (ASCII 文本: GET /path HTTP/1.1\r\n...)

  选择 HTTP/2 → Repeater 用 HTTP/2 帧格式构造请求
                (二进制帧: PRI * HTTP/2.0... + HEADERS 帧)
```

**关键区别**：

| | h2csmuggler.py | Burp Repeater (HTTP/2 模式) |
|---|---|---|
| **通信路径** | 直接通过 TCP 发送 h2c Upgrade → 101 → H2 帧 | TLS-ALPN 协商 h2 → 直接发 H2 帧 |
| **是否走 Upgrade 路径** | 是（先 HTTP/1.1，升级到 h2c） | 否（TLS 握手时 ALPN 已经协商为 h2） |
| **代理行为** | 被 101 踢入隧道模式（盲传） | 全程处于 HTTP/2 帧解析模式（可见） |
| **能否绕过代理 ACL** | 能 | 不能 |

**结论**：Burp Repeater 选择 HTTP/2 只是改变了请求的**编码格式**，但沟通路径仍然是标准的 h2（TLS-ALPN），代理从头到尾都在解析。**只有通过 h2c Upgrade 路径（即先用 HTTP/1.1 发 Upgrade 请求）才能触发代理的隧道模式盲传。** h2csmuggler 的价值在于它可以绕开浏览器/标准 HTTP 库对"禁止在 HTTPS 上发 h2c Upgrade"的限制，直接构造 TCP 层面的 HTTP/1.1 请求来完成 Upgrade。

## 12. 隧道模式下能否发 HTTP/1.1？代理盲传 ≠ 后端理解

### 12.1 直觉上的推理

```
代理返回 101 后进入隧道模式 → 代理不再解析后续内容 → 后续发什么代理都盲传
                                                      ↓
                                          那我发 HTTP/1.1 格式的请求
                                          代理也应该盲传，后端应该处理？
```

### 12.2 实际情况：代理确实盲传，但后端已经不在 HTTP/1.1 了

```
客户端                    代理（隧道模式）              后端
  │                         │                          │
  │  ════ TCP 盲传 ════════╪══════ TCP 盲传 ═══════════│
  │                         │                          │
  │  ──── HTTP/1.1 ────────→│ ──── HTTP/1.1 ──────────→│
  │  GET /admin HTTP/1.1    │ GET /admin HTTP/1.1     │
  │  Host: ...              │ Host: ...                │
  │                         │                          │
  │                         │              后端状态机: HTTP/2 解析模式
  │                         │              期望收到二进制帧（9 字节帧头）
  │                         │              收到 ASCII 文本 `GET /admin...`
  │                         │              → 无法解析 → 连接断开或出错
```

**核心**：代理的"隧道模式"和后端的"协议状态"是**两个独立条件**，必须同时满足才能攻击成功。

| 条件 | 代理隧道模式 | 后端仍在 HTTP/1.1 |
|------|:----------:|:----------------:|
| h2c 走私（成功升级） | ✅ | ❌（已切 HTTP/2） |
| WebSocket 走私（场景一）| ✅ | ✅（Upgrade 失败，未切换）|

### 12.3 WebSocket 走私（场景一）的特殊之处

这正是 WebSocket 走私（场景一）与 h2c 走私的关键差异：

```
客户端                    代理                       后端
  │                         │                          │
  │  ──── Upgrade websocket ─→│ ──── Upgrade websocket ──→│
  │     Sec-WebSocket-Ver: 99 │  Sec-WebSocket-Ver: 99   │
  │                         │                          │
  │                         │        后端: 版本 99 不存在
  │  ←─── 426 UpgradeReq ────│ ←─── 426 UpgradeReq ──────│
  │                         │                          │
  │          代理: "有响应了，进隧道！"                    │
  │          （不校验必须是 101！）                        │
  │                         │                          │
  │  ═══ TCP 盲传 ══════════╪══════ TCP 盲传 ═══════════│
  │                         │                          │
  │  ──── HTTP/1.1 ────────→│ ──── HTTP/1.1 ──────────→│
  │  GET /admin HTTP/1.1    │ GET /admin HTTP/1.1     │
  │                         │                          │
  │                         │              后端从未切换协议
  │                         │              仍在 HTTP/1.1 模式
  │                         │              → 正常处理请求！
```

**对比**：

| | h2c 走私 | WebSocket 走私（场景一） |
|---|---|---|
| 响应码 | 101（升级成功） | 426（升级失败） |
| 后端实际状态 | 已切换到 HTTP/2 | **从未切换，仍在 HTTP/1.1** |
| 代理状态 | 隧道模式（盲传） | 隧道模式（盲传） |
| 后续能否发 HTTP/1.1？ | 不能（后端在等 HTTP/2 帧） | **能**（后端还是 HTTP/1.1） |
| 后续攻击必须用什么格式？ | HTTP/2 二进制帧 | 普通 HTTP/1.1 文本 |

### 12.4 总结

**代理盲传**和**后端理解**是两个独立条件：

- 代理隧道模式只解决了"代理不拦截"的问题
- 后端协议状态决定了"发什么格式后端才能理解"

h2c 走私场景中，因为 Upgrade 真正成功了（后端返回 101 且切换了协议），后续**必须用 HTTP/2 帧格式**发送请求。WebSocket 走私场景一中因为 Upgrade 失败了（后端返回 426，未切换协议），后续可以继续用 HTTP/1.1 —— 这正是 WebSocket 走私比 h2c 走私更易于利用的原因之一。
